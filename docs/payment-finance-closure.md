# 支付与财务闭环：实现及上线边界

更新：2026-08-31。对应 Platform Alembic `0049_payment_finance_closure`。

本轮落地的是可持久化、可重放、有失败保护的支付与财务状态机，以及 SQLite/真实 PostgreSQL 回归。没有连接真实商户扣款，没有授权生产切流。`10 积分 = ¥1` 不变；现金仍用人民币整数分记录，积分不是现金余额。

## 1. 退款与拒付

- 退款请求先在原购买批次上预占可退权益。PSP 超时或结果未知不等于失败：保留退款占用，通过原请求身份查询，不能换幂等键再次退款。
- 成功退款与有效拒付的累计金额不能超过实收；创建新退款时还要扣除结果未知或在处理中的退款占用。应用事务与数据库总额约束共同检查。
- 不能把已消费、已预占或不具现金依据的积分当作可退款余额。促销及无法证明现金来源的历史赠送积分不可退款。
- 拒付扣回未用积分，不足部分形成该笔拒付的债务。后续充值先按明确分配偿债，只把剩余积分放入可用余额。
- 每次偿债形成不可变 `PaymentDisputeDebtRecoveryAllocation`，拒付胜诉按原分配写 `PaymentDisputeDebtRecoveryReversal`。不能用钱包总债务猜测某笔拒付恢复多少，也不能改写旧账本。
- 企业发票支付、退款、拒付、胜诉同步维护应收分录与发票/账期投影；部分回款不等于结清。

## 2. 持久化支付投递

客户的创建支付/退款请求返回 `202`，表示意图已经持久化，不表示扣款或退款成功。

1. 同一数据库事务写订单/退款与 `PaymentProviderCommand`。
2. Worker 用 `SKIP LOCKED` 领取单条命令，保存随机 lease token，提交事务。
3. 离开数据库事务后调用 PSP；重试沿用固定操作身份和请求摘要。
4. 新事务按命令及 lease token 验证所有权，再更新结果、交易、积分与账本。失效租约不得回写。
5. 崩溃、网络超时或不确定返回进入查询/核对路径；结果未证实前不释放退款权益，不发第二笔自动充值。

Outbox 的商户、目标、操作、幂等键、原始请求和摘要不可改写。状态、重试时间、租约及结果字段可以推进；不能删除原记录。PostgreSQL 也禁止对支付与财务事实执行 `TRUNCATE`。

Webhook 验签后先落 `PaymentWebhookInboxEvent`，再独立处理。验证结果必须绑定已配置的 provider、merchant、key 与事件身份；客户不能自报“已验签”。同事件同内容为精确重放，同事件不同内容拒绝。乱序到达的依赖事件保存为阻塞项，待前置事实到达后重放。数据库事务把处理结果、不可变 receipt 及资金/积分事实一起提交；旧查询结果不能回退已确认的终态。

当前注册器没有默认真实 PSP，也不会回退为测试通道。生产不能启用测试适配器。厂商适配器还必须用真实 PSP 的幂等、查询、金额与时间证据满足同一协议；仅有一个 HTTP 成功响应不算支付结算事实。

## 3. 外部文件与全链对账

内部导入接口接收实际文件 bytes（HTTP 使用 Base64），服务端校验大小、计算 SHA-256、严格解析并保存不可变原文件。当前支持版本化的规范 JSON：

- `payment-settlement-json-v1`：PSP 资金、独立手续费、Payout、银行入账。
- `provider-cost-json-v1`：供应商账户、原始作业引用、通道、任务及实际成本。

文档中的 provider/merchant 或 supplier/account、币种、期间及行数据必须与批次声明一致。调用方给出的摘要与大小只是待验证声明；对象路径和版本仅为定位信息，不替代真实文件。重复导入在 PostgreSQL 唯一键竞争下仍只生成一个批次；同文档身份不同 bytes 或不同元数据为冲突，不覆盖旧批次。

上传通路只会记录 `uploaded_file_digest`，不允许调用方选择“provider_signature”或伪造验证时间。保存原件证明了“本次到底导入了什么”，不证明它由 PSP/银行/供应商签发。缺少可信来源适配时，即使金额全部匹配，也保留 `SOURCE_AUTHENTICITY_UNVERIFIED`，不能得到无例外的 `BALANCED`。

对账结论绑定精确批次与摘要，重放时重验保存的文件和解析结果。检查范围包括：

| 维度 | 核对内容 |
| --- | --- |
| 资金 | 实收、退款、拒付与撤销，PSP 明细及应收支付事实 |
| 积分 | 发放、偿债、可用、任务预占、退款占用、结算、反向分录 |
| 任务 | 报价版本、成功结算、失败释放及批次价值分摊 |
| 供应商成本 | 实际作业成本与供应商账单；不使用客户售价推算成本 |
| 清结算 | 手续费、Payout 汇总及独立银行到账证据 |

缺证据、金额不符、孤立交易、重复归属或来源未认证都形成结构化例外。最终结论不能原地修改，后补证据需要新的核对运行；备注“已处理”不能篡改原事实。

## 4. 自动充值与企业月结

自动充值必须绑定 `PaymentMandate`：客户只能创建待授权意图；受信服务携带匹配的同意版本/摘要及 PSP customer、payment method、mandate 引用激活。仅有客户编号不具备离线扣款授权。用户可以撤销授权；Worker 在首次扣款前重新验证，已发出的未知请求则继续查询，不伪装成未扣款。

规则有阈值、单次额度、月度上限、冷却与持久化执行记录；尚未确定结果的订单阻止再次自动补款。检查时间与扣款尝试时间分开记录，未触发的规则不能一直占住扫描队列前部。PSP 的授权页面、实际签约证据和外部撤销仍由选定 PSP 的适配器提供，不能把内部激活入口当成用户真实签约。

企业账期按已批准合同的时区和自然月边界运行，禁止重叠账期和提前关账。关账形成不可变明细与应收；后台逐月追赶漏跑账期而不重复增加授信。持久化日级催收记录驱动逾期及授信暂停。暂停后不能新增合同授信敞口或消耗原合同授信积分；仍允许使用符合规则的已付款/非授信积分，不吞掉客户现金权益。

催收运行记录和授信控制已实现；尚未发送短信、邮件或银行扣款提醒。真实通知通道必须另行接入，不把数据库 action 记录描述为“客户已收到通知”。

## 5. Worker 与权限

`python -m platform_api.billing_worker` 是 HTTP-only 调度进程，没有数据库或 PSP 凭据。它调用固定的内部入口：

- `/internal/billing/payment-webhook-inbox/run-once`
- `/internal/billing/payment-provider-commands/run-once`
- `/internal/billing/auto-recharge/run-once`
- `/internal/billing/enterprise/run-once`

参数为 `--platform-url` 与 `--service-token-file`；可用 `--jobs` 限定队列、`--once` 单次运行。令牌从绝对路径文件逐次读取，支持受控轮换；不允许令牌出现在参数或日志。默认要求 HTTPS，不跟随跳转、不继承环境代理。仅显式 `--allow-loopback-http` 可用于本机 HTTP。单个队列临时失败不会阻止其余队列；鉴权/协议错误则停止。

Worker 尚未代替部署人员发布为生产常驻服务。上线仍需进程监督、队列积压与未知结果告警、密钥轮换、运行审计及恢复演练。

## 6. 迁移与生产门禁

`0049` 对历史数据保持失败关闭：若存在没有原件绑定的旧结算行，或没有 Mandate 的历史自动扣款订单，迁移会在 DDL 前停止。必须制定保留历史的操作员迁移方案；不能删除旧支付事实、捏造原件或补造用户同意来绕过检查。

新增 v14 数据库权限/行为清单已经随迁移和约束落地，但生产 catalog 指纹仍为 `UNQUALIFIED`；受保护生产运行不会把它视为已认证。开发 PG16 迁移与并发测试通过，不等于生产角色、签名发布证明及实际环境已经通过。

生产还需要以下独立证据，当前未宣称完成：

1. 选定 PSP 的商户、签约、回调验签、查询、超时、真实退款/拒付验收。
2. PSP、银行及供应商原始账单的可信获取/签名验证，以及实际到账抽样。
3. v14 受保护 PostgreSQL catalog/角色和发布证明资格。
4. 常驻 Worker、监控、通知与备份恢复演练；完整 staging 对账后再决定生产启用。

并发门禁使用与产品一致的 `autoflush=False`、`expire_on_commit=False`。已覆盖先读旧 ORM 快照再加锁、退款与任务预占锁竞争、新充值偿还旧拒付债务与胜诉竞争、重复文件导入、月结/催收竞争。拿到行锁后必须读取最新投影，不能继续计算锁前缓存。
