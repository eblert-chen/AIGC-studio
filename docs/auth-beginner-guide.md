# 零基础读懂项目登录系统（小白教程）

> 适用对象：完全不懂技术的初学者。
> 目标：让你看懂「用户怎么登录我们这个 AI 视频平台」，以及为什么要用好几样看起来很像的技术。
> 配套记忆：本项目登录采用 **OIDC/OAuth2 登录 + 服务端 Session**，JWT 只在登录那一刻用一次。详见 `docs/` 与项目记忆。

---

## 0. 先说人话：登录到底在解决什么问题？

想象一个系统（比如你的 AI 视频平台）。它每天要回答三个问题：

1. **你是谁？**（确认身份，不是冒充的）
2. **你已经进来了吗？**（记住登录状态，别让你每点一下都重新输密码）
3. **你现在做的事，允许做吗？**（权限检查）

「登录系统」就是专门负责第 1、第 2 件事的那套机制。本项目把这件事拆成三样东西配合完成，下面一个个讲。

## 1. 名词小词典（每个都配一句大白话）

| 名词 | 一句话解释 | 生活类比 |
|---|---|---|
| **认证 (Authentication)** | 证明"你真的是你" | 酒店前台核对你的身份证 |
| **授权 (Authorization)** | 确认"你能做某件事" | 房卡只能开你自己的房门，不能开别人 |
| **身份提供商 / IdP** | 专门负责"证明你是谁"的外部机构 | 公安局（发身份证的地方） |
| **OIDC (OpenID Connect)** | 在 OAuth2 上面加了一层"你是谁"的协议 | 一套标准的"办入住"流程 |
| **OAuth 2.0** | 一套"授权"标准，负责把登录流程安全地跑完 | 入住流程里的"核验+发卡"步骤顺序 |
| **JWT (JSON Web Token)** | 一段被签名的、防篡改的文字证明 | 身份证本身（有防伪签名，谁都能看但改不了） |
| **ID Token** | IdP 用 JWT 格式开的"这是某某人"的证明 | 公安局开给你的、带防伪的身份证明 |
| **JWKS** | IdP 公开的一把"验签公钥"清单 | 公安局公布的验钞机/验伪设备 |
| **RS256** | 一种"用私钥签名、用公钥验签"的算法 | 防伪印章 + 对应验伪工具 |
| **Session (会话)** | 登录成功后，服务器记住"这个人已登录"的一段记录 | 酒店发给你的房卡 + 后台登记 |
| **Cookie** | 浏览器自动替你保存的一小条数据，每次访问网站自动带上 | 你随身带的房卡 |
| **HttpOnly** | 这条 Cookie 只能用、不能用脚本读（防小偷用代码偷） | 房卡锁在贴身口袋，程序碰不到 |
| **Secure** | 这条 Cookie 只在 https（加密连接）下才发送 | 只在安全通道里出示房卡 |
| **SameSite** | 限制 Cookie 只在"同网站"请求里带，防别人网站冒用 | 房卡只在自家酒店大门刷 |
| **__Host- 前缀** | 强制这条 Cookie 只能由网站主域名设置，防冒名 | 房卡上印死"仅本酒店有效" |
| **CSRF (跨站请求伪造)** | 坏人骗你的浏览器，偷偷用你的身份发请求 | 有人拿你的房卡照片去前台冒刷 |
| **CSRF Token** | 每张网页藏一个随机暗号，写操作时必须带上，证明"这真是你点的" | 每次开门还要对一句暗语 |
| **PKCE** | 登录时生成的一对"随机谜面+答案"，防止中间人偷走授权码 | 入住时前台和你各拿一半拼图，缺一半无效 |
| **nonce** | 一次性的随机数字，防止同一份证明被重复使用 | 每次办证换一个新水印 |
| **WebAuthn / passkey** | 用指纹/人脸识别或物理密钥登录，比密码更安全 | 刷脸开门，不用记密码 |
| **amr** | "你刚才用了哪种方式登录"的记录 | 登记上写"此人刷脸进入" |
| **step-up (逐步升级认证)** | 做危险操作前，要求你再验一次身份 | 进金库前再刷一次脸 |
| **吊销 / 黑名单** | 让已经发出的凭证立刻失效 | 房卡挂失，马上刷不开 |

> 小提示：Authentication（认证）和 Authorization（授权）中文都带"权"字，容易混。记住一句话：**认证=你是谁，授权=你能干啥**。本项目登录只管"你是谁 + 你已登录"，"你能干啥"是另一套权限系统管的事。

## 2. 核心类比：住酒店

把登录想成住酒店，三样技术各管一段：

| 技术 | 在酒店里是谁 | 干什么 |
|---|---|---|
| **OIDC / OAuth2** | 前台核验身份的流程 | 让你出示身份证、走完入住手续 |
| **JWT（ID Token）** | 身份证本身 | 公安局开出的、带防伪签名的"你是谁"证明 |
| **Platform Session** | 酒店发的房卡 + 后台登记 | 确认你住店后，给你一张卡，之后开门刷这张卡 |

**最关键的一句话：**
你**不会每次开房门都重新出示身份证**。同样，用户**不会每次调用平台都重新走一遍登录**。

- 身份证（JWT）只在"办入住那一刻"用一次，验完就收走。
- 之后你开门，刷的是**房卡（Session）**。
- 房卡丢了（退出登录 / 账号被停用），前台（服务器）在登记簿上一划，卡立刻失效——不用等身份证过期。

## 3. 一次完整登录，经历了什么？（按时间顺序）

下面把"你点一下登录"到"你能用平台"的全过程展开。跟着数字看：

1. **你点「登录」** → 浏览器告诉平台："我要登录。"
2. **平台把你转向 IdP**（身份提供商，比如企业统一登录、Auth0、Keycloak 等）→ 这一步叫 OAuth2 的"授权码 + PKCE"流程，平台同时记下 `state`（防掉包）和 `nonce`（防重用）。
3. **你在 IdP 那里登录** → 可能输密码，也可能刷脸（WebAuthn/passkey）。这是 IdP 的事，平台完全不碰你的密码。
4. **IdP 把你转回平台**，附带一个"授权码"(code)。
5. **平台拿 code 去换 ID Token** → IdP 返回一张 **JWT 格式的 ID Token**（带 RS256 签名）。
6. **平台验这张 ID Token** → 用 IdP 公开的 **JWKS 公钥**核对签名，并检查签发者(iss)、接收方(aud)、一次性水印(nonce)都对得上。
7. **平台创建 Session** → 在数据库写一条"某人已登录"的记录（只存密码学摘要，不存原文），并生成一张"房卡"。
8. **平台把房卡交给浏览器** → 写进 Cookie（`__Host-ai_video_session`，带 Secure/HttpOnly/SameSite 等安全属性）。
9. **之后你每次操作** → 浏览器自动带上这张房卡 Cookie，平台查数据库确认"房卡有效、人还活着"，就放行。

> 注意第 5–7 步：**JWT 在第 6 步验完就完成任务了，前台不会把身份证塞回给你带走。** 浏览器手里只有房卡（Session Cookie），没有长期 JWT。这是本项目刻意的安全设计。

## 4. 为什么要用三种技术，而不是只用一个？

这是最容易困惑的地方。下面反过来问："如果只用其中一种，会怎样？"

### 场景 A：只用 JWT（不用 Session）
可以设计成：登录后浏览器保存 JWT，每次请求都带它。
问题：
- JWT 一旦签发，在过期前通常一直有效。**你点"退出全部设备"，旧的 JWT 可能还能用。**
- 要"立即吊销"，就得额外建黑名单或版本表——**到最后，又变回了 Session。**
- JWT 如果放浏览器本地存储(localStorage)，网站被 XSS 攻击时更容易被脚本偷走。
- 如果 JWT 有效期设很短，又得引入"刷新令牌"(Refresh Token)，系统反而更复杂。

### 场景 B：只用 Session（不用 OIDC）
传统网站常这样：用户名密码 → 平台自己验证 → 建 Session。
问题：平台就得**自己变成一个完整的身份系统**，自己负责：
- 密码保存与加密
- 找回密码
- 邮箱验证
- 多因素认证(MFA)
- WebAuthn/passkey
- 企业单点登录(SSO)
- 账号锁定、异常登录防护
- 身份提供商密钥轮换
**安全责任大到吓人。** 而用 OIDC，这些全交给专业 IdP。

### 场景 C：只用 OIDC/OAuth2（不建自己的 Session）
问题：
- 浏览器得接触并保存 IdP 的 Token。
- 平台会和某个 IdP 的 Token 生命周期**强绑定**，很难独立管理"当前设备/全部设备"。
- 平台想"全局停用用户"时，IdP 的 Token 可能还有效。
- 平台自己的权限变更，不容易立刻反映。
- IdP Token 里可能含不该暴露给前端的敏感信息。

### 本项目怎么选？——三件套组合
| 技术 | 负责 |
|---|---|
| **OIDC** | 证明"登录者是谁"、跑完登录流程 |
| **JWT** | 传递一次"经过签名的身份声明"，平台验完即弃 |
| **Session** | 维持平台内部的登录状态（房卡） |

于是同时拿到这些好处：
- 企业统一登录（SSO）
- WebAuthn/passkey 强认证
- JWT/JWKS 签名验证（防伪）
- **浏览器不保存 IdP Token**（XSS 偷不到）
- 当前设备立即退出
- 全部设备立即退出
- 平台全局停用立即生效
- 独立的"空闲过期"和"绝对过期"
- 管理员做危险操作时要求重新认证(step-up)
- 前端无法通过改用户 ID 冒充别人

代价：代码和数据库比"纯 JWT"稍复杂——但这是为了达到生产级安全必须付的。

## 5. 登录之后，每次请求怎么被检查？（保安查房卡）

你每点一次按钮，平台都会在后台快速做这些检查（全部自动，你无感）：

1. **房卡在不在？** —— Cookie 里的 Session Token 有没有。
2. **房卡是真的吗？** —— 数据库里有没有对应的摘要记录。
3. **这张卡挂失了吗？** —— Session 有没有被撤销(revoked)。
4. **人还在吗？** —— 用户账号是否仍是 ACTIVE（没被停用）。
5. **版本对吗？** —— auth_version 是否匹配（改密码/权限后会变，旧卡自动失效）。
6. **过期了吗？** —— 绝对有效期（比如登录 7 天强制重登）和空闲有效期（比如 30 分钟没动就登出）到了没。
7. **危险操作要再验一次吗？** —— 高风险动作要求 auth_time（上次认证时间）足够新，否则弹窗让你再登录一次(step-up)。
8. **管理员刷脸了吗？** —— 平台管理员的高风险请求，要求登录时的 amr 含 WebAuthn/passkey 等强认证方式。

因为每次都查数据库 Session，**所以"停用账号"或"退出全部设备"能立刻生效**——不用等任何 Token 慢慢过期。这是纯 JWT 方案做不到的。

## 6. 房卡本身的安全属性（Cookie 设置）

平台下发的 Session Cookie 带这些"防伪标签"：

| 属性 | 作用 |
|---|---|
| **Secure** | 只在加密连接(https)下发送，明文网络里不出现 |
| **HttpOnly** | 不能用 JavaScript 读取，防 XSS 偷走 |
| **SameSite=Lax** | 别的网站发起的请求不带它，防 CSRF 冒用 |
| **Path=/** | 全站有效 |
| **__Host- 前缀** | 只能由主域名设置，防子域冒名下发 |

另外，做"写操作"（发视频、改设置等）时，网页里还藏着一个独立的 **CSRF Token**，必须随请求一起带上，平台比对一致才放行——等于"刷房卡还要对一句暗语"，进一步防冒用。

## 8. 常见小白疑问

**Q：那 new-api 控制台的登录（root/123456）和这个是一回事吗？**
A：不是。new-api 是另一套独立系统，用自己的账号密码登录，和平台登录完全分开。你给平台用的是 new-api 里生成的"令牌(Token)"，不是它的登录账号。

**Q：localStorage 是什么？为什么不能放 JWT 那里？**
A：localStorage 是浏览器里一块"脚本随便读"的存储。JWT 放那里，一旦网站被注入恶意脚本(XSS)，脚本就能把 JWT 偷走、冒充你。本项目不让浏览器长期持有 JWT，从根上避开这个坑。

**Q：为什么不直接用微信/QQ 登录？**
A：可以，但那也是"换一个 IdP"而已。底层还是 OIDC/OAuth2 那套流程，只是把"企业 IdP"换成"微信"。本项目的架构支持接入任意兼容 OIDC 的 IdP。

**Q：我本地想最快跑起来看效果，怎么办？**
A：两条捷径（都不走正式 OIDC）：
- 开 `VITE_ENABLE_DEMO=true` → 内置一个 demo 身份，免登录。
- 或开 `AUTH_LEGACY_BEARER_ENABLED=true` → 用本地 JWT 模式（仅开发，生产禁用）。

**Q：为什么我之前配 new-api 时一直弹"网络错误"？**
A：那是 new-api 控制台自身的问题（可能是 Docker 容器、端口、或它前端连后端地址配置），和本平台的登录系统无关。需要的话我可以帮你排查。

## 9. 一句话总结

> **OIDC 是前台核身份证，JWT 是那张带防伪的证明，Session 是酒店发给你的房卡。**
> 三者不是重复建设，而是前后衔接：IdP 只出现在登录边界，验完身份，平台用自己的房卡(Session)管你之后的每一次访问。

这样，你既享受了专业身份机构的安全（企业 SSO、刷脸、签名防伪），又拥有平台自己可控的会话管理（随时踢人、立即停用），还把"浏览器偷 Token"的风险压到了最低。
